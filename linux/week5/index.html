STEP 1｜使用者瀏覽器 ＆ DNS（q3.qqnice.org）

在這一步發生什麼事：學生或管理員在瀏覽器輸入 https://q3.qqnice.org，DNS 將 q3 解析到與 q1 相同的 Ubuntu VM 公網 IP，封包送往主機的 443 埠。

驗證方式：dig +short q3.qqnice.org A AAAA

⚠️ 這一站的安裝注意事項： 確認 q3 的 A 記錄指到正確公網 IP，並檢查是否有錯誤的 IPv6 (AAAA) 記錄導致憑證驗證或連線失敗；管理員須先完成首帳號註冊並關閉任意開放註冊後，再讓學生登入。

Firewall & Connection Fix / 02

為什麼「設了防火牆／容器連 Host」還是連不上？

Open WebUI（跑在 Docker 容器）要連 Ubuntu Host 上的 Ollama（:11434），必須同時打通「名稱解析」→「Ollama 監聽範圍」→「UFW 正確來源網段」三關。點選下方三個最常卡住的原因查看解法：

點選檢查：常見卡關原因與正解

解析原因 1：為什麼放行 172.17.0.0/16 還是被 UFW 擋掉？

在 Linux Docker 中，extra_hosts: ["host.docker.internal:host-gateway"] 會把名稱指到預設 docker0 的 IP（通常是 172.17.0.1）。

但是！ Docker Compose 會為專案建立獨立的 Bridge 網路（例如 172.18.0.0/16 或 172.19.0.0/16）。當 Open WebUI 容器連線至 172.17.0.1:11434 時，封包的來源 IP 是 Compose 網路的 172.18.0.x。如果你在 UFW 只放行 172.17.0.0/16，UFW 就會把來自 172.18.0.x 的封包直接丟棄！

正確查網段與 UFW 放行指令 
# 方法 A（最精準）：查出 WebUI 所在 Docker 網路的真實子網並放行
docker network inspect llmnet -f '{{range .IPAM.Config}}{{.Subnet}}{{end}}'
# 假設印出 172.18.0.0/16，則放行該子網：
sudo ufw allow from 172.18.0.0/16 to any port 11434 proto tcp

# 方法 B（通用 Docker 私網段）：放行本機 Docker 橋接私網段範圍 (172.16.0.0/12)
sudo ufw allow from 172.16.0.0/12 to any port 11434 proto tcp
sudo ufw reload && sudo ufw status numbered

Installation Precautions / 03

安裝與整合時的「六大注意事項」提醒

注意事項 01 · Host 服務

Ollama 交給 systemd 管理，且須調整監聽

  • 正式服務由 systemd 常駐管理，可用 systemctl status ollama 與 journalctl -u ollama 追查日誌。
  • 必須透過 systemctl edit ollama.service 設定 Environment="OLLAMA_HOST=0.0.0.0:11434"（或容器可達之 Host 位址），否則預設 127.0.0.1 容器連不進來。
切勿：不要在 SSH 終端機裡手動執行 ollama serve 當作正式服務（關掉視窗就斷線）。
注意事項 02 · 防火牆與連接埠

鎖住 11434 與 8080，只開放 q3 的 443

  • Open WebUI 不對公網發布 3000 或 8080 埠，只透過專用 Docker 網路給 Nginx 連。
  • 當 Ollama 改聽 0.0.0.0:11434 前，先確認 UFW 與雲端防火牆已阻擋外部公網連入 11434，僅放行 Docker 容器網段（並核對 IPv4 與 IPv6）。
切勿：不要以為「q3 有設 HTTPS 密碼」就安全——若 11434 暴露在公網，任何人都能繞過網頁直接偷用算力。
注意事項 03 · 既有 Nginx 與串流

沿用既有 Nginx，必開 WebSocket 與關緩衝

  • 與原有雙網站共用同一個 Nginx 容器，將 Nginx 與 Open WebUI 加入同一個專用外部 Docker 網路。
  • 先確認憑證有效再啟用 HTTPS；設定檔須加上 Upgrade / Connection "upgrade"（支援 WebSocket）與 proxy_buffering off（支援逐字串流）。
切勿：不要在 ~/llmstack 再開第二個搶占 80/443 埠的 Nginx；且務必先 nginx -t 通過才 reload。
注意事項 04 · 硬體資源與共存

模型檔案大小 ≠ 記憶體用量，須保護原雙網站

  • 先從小型量化模型與單人有限上下文開始測試，並用 ollama ps 確認實際跑在 CPU 或 GPU。
  • 長對話與多人同時提問會大幅增加記憶體消耗，務必預留 RAM 給原有的雙網站與 MariaDB。
切勿：不要只看裝了 GPU 驅動就以為模型跑在 GPU；也不要一次載入過大模型導致整台 VM OOM 當機。
注意事項 05 · 帳號與版本控管

先建管理員再公開入口，鎖定映像版本

  • Open WebUI 啟動後，先在限制來源下建立第一個管理員帳號，並將新註冊改為「管理員審核」或預建一般帳號。
  • 固定保存 WEBUI_SECRET_KEY，並固定 WebUI 映像版本與 Digest（不依賴浮動標籤）。
切勿：不要在還沒建立管理員前就把網站公開到公網（第一個註冊的人會直接變成管理員！）。
注意事項 06 · 備份還原與退場機制

獨立 Volume 停機備份，失敗時安全回退

  • 上週的 WordPress 備份腳本不會自動備份本週的 WebUI Volume。備份時先停 WebUI 容器，再打包 Volume。
  • 還原驗證請掛載到「獨立測試 Volume」，不要直接覆蓋正式對話資料。
切勿：萬一整合出錯，只需退回新增的 q3 設定並停掉新服務；絕不要刪除原 Volume 或重設整套防火牆！
