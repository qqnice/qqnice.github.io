鑑識 1：從 HTTP 狀態碼看穿「暴力破解失敗」與「憑證外洩一擊登入」

在 WordPress 中，對 wp-login.php 發送 POST 時：若回傳 HTTP 200 代表停留在登入頁（登入失敗）；若回傳 HTTP 302 代表驗證成功並跳轉至 /wp-admin/。

統計全部 164 次 POST 發現：129.212.229.61 在 10/23 晚間狂試 138 次全回 200（失敗）；但 10/24 05:20 起，卻有 5 個不同 IP 各只送出 1 次 POST 就拿到了 302 成功登入！這證明攻擊者進場時手上已握有管理員 123 的有效帳密。

雙胞胎 IP 謎團：10:58:49 由 179.255.155.96 登入成功（302），但 13 秒後從未登入過的 179.255.151.96（僅差一碼）卻直接呼叫 admin-ajax.php 建立 3 個檔案，推測為同一攻擊者跨節點共用登入 Cookie！

Extended Maintenance Vulnerabilities / 03

延伸維護時的「八大漏洞與維運盲點」深度剖析

除了帳密外洩本身，這次事件更暴露了日常維護、容器配置、備份策略與緊急應變時的 8 個延伸漏洞。點選分類篩選查看原因與根治方案：

維護漏洞 01 · 容器端口暴露

後端容器 `:8081` 直接對外開放（繞過 Nginx 風險）

  • 問題現象：WordPress 容器的 8081 埠原本直接對外開放。雖然 5 個登入成功的 IP 在 Nginx log 都有紀錄（代表走 80/443），但容器 log 在 10/23 01:48 抓到一筆來自 212.73.148.8 的 TLS 握手亂碼請求（回 400），而 Nginx log 完全沒有這個 IP！
  • 延伸風險：證明外部掃描器已經直接掃到 8081！一旦未來在 Nginx 設定了 IP 白名單或 WAF，攻擊者只要改連 :8081 就能輕鬆繞過所有防護。
✅ 根治方案：後端容器絕不對公網 publish 埠號（移除 0.0.0.0:8081->80，或僅綁定 127.0.0.1:8081:80 供本機測試），統一只由 Nginx 反向代理透過內部 Docker 網路連線，並在雲端 NSG 關閉 8081。
維護漏洞 02 · Volume 命名與殘留陷阱

使用匿名 Volume (`5d00e04c…`) 且誤以為 `tar` 解壓能還原乾淨

  • 問題現象：qqnice-wordpress 掛載的是 64 字元匿名 Volume 5d00e04c…，而主機上另有 wordpress_site_wordpress_data 與 webstack_wp-data，多份 Volume 散落極易搞混。
  • 延伸風險：維護還原時若直接對舊 Volume 執行 tar -xzf wp-data.tar.gz，tar 只會覆蓋同名檔案，絕對不會刪除攻擊者新增的後門檔案！且本次受駭 Volume 已被整批 chmod 777 與改寫核心檔。
✅ 根治方案：在 compose.yml 明確宣告具名 Volume；被入侵後的 Volume 視為完全不可信任（僅保留供鑑識，絕不搬移任何檔案回去），還原時必須建立全新空白 Volume 再解壓乾淨備份。
維護漏洞 03 · 主機與容器環境混淆

在容器化 Host 誤裝 `python3-certbot-apache` 並對錯的 Nginx 下指令

  • 問題現象：10/23 12:21 執行 apt install certbot python3-certbot-apache -y，導致 Ubuntu 主機被裝入整套 apache2 並自動啟動 apache-htcacheclean（以 www-data 執行），主機 apache2 則因 80 埠被佔用啟動失敗；同日 19:32 修改設定後多次執行 sudo systemctl reload nginx，但主機的 nginx 其實是 inactive（真正在跑的是容器內的 nginx）。
  • 延伸風險：Host 與容器職責混淆，不僅讓設定重載失效，更在資安鑑識 ps aux | grep www-data 時出現幽靈程序干擾判斷！
✅ 根治方案：反向代理既已容器化，重載應使用 docker exec <nginx容器> nginx -t && docker exec <nginx容器> nginx -s reload；申請憑證應使用純 certbot (webroot/standalone) 而非安裝會夾帶主機 Web Server 的 python3-certbot-apache。
維護漏洞 04 · 備份範圍落差與單點風險

手動備份漏掉 `config.tar.gz`（Nginx/憑證），且初期缺乏離機副本

  • 問題現象：標準講義的 backup.sh 會產出 5 個檔案（含文章清單 posts.tsv、檔案雜湊 wp-files.sha256、設定檔 config.tar.gz）。本次手動備份只打包了 db.sql 與 wp-data.tar.gz，使 SHA256SUMS 只有兩行，漏掉了 Nginx 反向代理設定與 SSL 憑證。
  • 延伸風險：若整台 VM 毀損，雖有網站資料卻得重新設定 Nginx 與憑證；且若備份只放在雲端 VM 上，一旦攻擊者取得 Host 權限連備份一起加密或刪除就會全軍覆沒。
✅ 根治方案：遵循 3-2-1 備份原則，第一時間將乾淨備份下載回個人電腦離機保存並核對 SHA256（已於 10/28 完成！），並將 Nginx 設定檔、compose.yml 與憑證納入自動化備份腳本。
維護漏洞 05 · 身分驗證與登入端點暴露

使用好猜的帳號代稱 (`123`)、疑似密碼外洩／共用，且 `wp-login.php` 全網公開

  • 問題現象：管理員帳號命名過於簡單（123），且 5 組外部 IP 不需暴力猜測就能「1 次 POST 回 302」直接登入，高度懷疑密碼強度不足或與其他曾外洩的服務共用密碼。
  • 延伸風險：wp-login.php 與 xmlrpc.php 對全網開放，不僅引來 5 分鐘 138 次 POST 暴力破解與 18 次 XML-RPC 呼叫，一旦憑證外洩更是門戶大開。
✅ 根治方案：重建後停用舊管理員帳號名稱，改用獨特帳號 + 16 字元以上獨立隨機強密碼 + 開啟雙因素驗證 (2FA)；並在 Nginx 設定 location = /wp-login.php 與 xmlrpc.php 僅允許管理員 IP 存取（其他人直接回 403）。
維護漏洞 06 · 後台權限擴張與檔案修改權限

後台允許直接上傳／安裝外掛（`wp-file-manager` 淪為毀站工具）

  • 問題現象：攻擊者進後台後，先用 update.php?action=upload-plugin 上傳後門壓縮檔，接著 209.50.170.195 直接在後台安裝 wp-file-manager (8.0.6)，讓後續的 179.255.155.96 能在 10 秒內發送 15 次 cmd=mkfile 建立惡意 PHP 並將整個 Volume 改為 777。
  • 延伸風險：只要一個管理員帳號或 Cookie 被偷，就等於取得容器內 www-data 的任意寫檔與執行程式碼 (RCE) 權限！
✅ 根治方案：網站穩定上線後，可在 wp-config.php 設定 define('DISALLOW_FILE_EDIT', true); 甚至 define('DISALLOW_FILE_MODS', true); 禁止從後台直接安裝外掛或改寫 PHP，外掛更新統一由維護期間短暫開啟。
維護漏洞 07 · 雲端防火牆緊急操作失誤

Azure NSG 規則誤把本人 IP 填在「目的地 (Destination)」導致斷線

  • 問題現象：10/24 13:19 發現入侵並準備鎖定 Azure NSG（限制 22/80/443/8081 只讓自己連）時，一時緊張誤把自己的公網 IP 填進「目的地 (Destination)」而非「來源 (Source)」。
  • 延伸風險：因為封包的目的地是 VM 的內網/公網 IP，不可能等於學生家裡的 IP，結果規則一生效就把包括自己在內的所有 SSH 連線全部擋死！
✅ 根治方案：修改雲端防火牆 (NSG / Security Group) 入站規則時，務必口訣核對：「誰連進來 ＝ 來源 (Source) 填我的 IP；連向哪台主機 ＝ 目的地 (Destination) 維持 Any / 主機 IP」，修改後於 13:53 順利恢復登入。
維護漏洞 08 · 鑑識時區與指令展開盲點

UTC 與台灣時間 (+8) 混用差一天，以及萬用字元未展開的「假 0 筆」

  • 問題現象：容器內與舊系統預設為 UTC，最初寄信給老師時看到後門檔日期為 10/15、10/6，換算為台灣時間 (+8) 其實是 10/16、10/7；此外在執行搜尋指令時，若萬用字元 (Glob) 因權限或引號未正確展開，終端機印出「0 個結果」其實是「根本沒讀到檔案」。
  • 延伸風險：8 小時的時差跨過午夜就會差一天，可能完全推翻「先備份還是先被入侵」的因果推論！
✅ 根治方案：所有資安報告與時間軸統一標註時區（如全頁統一換算為 UTC+8 並註明原始 log 為 UTC）；執行 grep 或 find 檢查無異常時，務必先用已知存在的關鍵字（如 Apache 啟動訊息 AH00163）確認指令真的有讀到資料！
