01

一、為什麼 Docker 還不夠？

Docker 解決了「怎麼把一個服務打包好、到哪都能跑」，但沒有解決「服務上線後誰來照顧它」。

🍳 廚房工作站的比喻

一個容器（Container）就像一座備齊廚具與食材的工作站，開起來就能出菜。但當餐廳客人突然暴增時，真正的問題才開始：

  • 誰決定什麼時候要再開幾座工作站？
  • 某座工作站突然停擺（Crash），誰發現並補上新的一座？
  • 客人進門後，誰負責把客人平均分配到不同的工作站？
🛠️ 只用 Docker vs 容器編排

只用 Docker 時，這些事都要人手動處理：自己多下幾次 docker run、自己改 Nginx 後端清單、半夜盯著容器有沒有掛掉。

Docker Compose 雖然能把多個容器寫進同一份檔案，但主要場景是單一主機，也不會依負載自動增減副本。這類自動化管理工作稱為容器編排（Orchestration），相當於全天候值班的餐廳經理。Kubernetes (K8s) 是被廣泛採用的編排系統，而 K3s 則是它的輕量版本。

🍳 互動實驗室 1：手動 Docker 大廚 vs K3s 自動餐廳經理

二、Kubernetes 的核心觀念：宣告期望狀態，系統負責達成

Kubernetes（簡稱 K8s）的做法是：你只描述「我要什麼樣子」（Desired State），系統持續讓現實（Actual State）貼近這份描述。本週任務會用到下列六個核心角色：

物件 (Object) 白話角色比喻 本週任務中的具體用途 互動檢視
Pod 最小排程單位 一座工作站，是 K8s 排程的最小單位，裡面跑一個或幾個緊密配合的容器 每個 Pod 跑一份 Open WebUI 容器
Deployment 「我要 N 座相同工作站」的訂單，底下由 ReplicaSet 維持副本數，也負責更新版本 宣告 Open WebUI 的映像檔、環境變數與資源需求 (requests)
Service 工作站的固定櫃台。Pod 會換（IP 會變），Service 的位址不變，並把流量分給就緒 (Ready) 的 Pod 給 Ingress 一個穩定的後端入口
Ingress 餐廳大門的接待，依網域與路徑把外部 HTTP 請求導向對應的 Service，需 Ingress Controller 執行（K3s 內建 Traefik） 讓 qN.qqnice.org 進得來並導向 Open WebUI Service
HPA 依忙碌程度自動調整訂單數量 (N) 的調度員 (Horizontal Pod Autoscaler) 依 CPU 使用率在 1 到 4 個 Pod 之間自動調整
metrics-server 提供各 Pod 用量的儀表板感測器 HPA 計算 CPU 使用率百分比的資料來源（kubectl top 也靠它）
🔍 點擊上方表格「查看 YAML 與細節」來預覽具體設定範例 具體實例說明
初學者常覺得 K8s 名詞很抽象。點選上方任一物件（例如 Deployment 或 HPA），這裡會顯示它在 Open WebUI 任務中實際長什麼樣子、以及它跟其他物件如何串聯！
🔄 互動實驗室 2：比對迴圈（Reconciliation Loop）與「自癒」原理模擬器

理解這些物件的關鍵是一個持續執行的比對迴圈，也就是任務書中的「自癒」原理：
1️⃣ 你宣告期望：Open WebUI 要有 N 個副本。 ➔ 2️⃣ 控制器持續比對「實際的副本數」和「期望的副本數」。 ➔ 3️⃣ 兩者不同就動手：少了就補，多了就收。
試著點擊「手動刪除 1 個 Pod」：這等於讓實際少了一個，觀察控制器如何在幾秒內發現差異並自動補上一個新的 Pod！

🎯 期望狀態 (Desired N) 3
📦 實際就緒 (Actual Ready) 3
⚖️ 控制器比對結果 一致 (In Sync)
readinessProbe 保護機制：新補上的 Pod 會先經過啟動與就緒檢查（黃燈），確認 Ready（綠燈）後 Service 才會把流量導過去，確保服務不中斷！

03

三、K3s 是什麼：把 Kubernetes 精簡打包成單一執行檔

K3s 是符合 Kubernetes 標準、可用於正式環境的輕量發行版，把非容器化的叢集元件整合成一個小於 100 MB 的單一執行檔。官方將它定位為「distribution（發行版）」而非 fork，目標是盡量貼近上游 Kubernetes（K3s 官方 README）。預設資料庫使用 sqlite3，也支援 etcd3、MariaDB、MySQL 與 Postgres。

🪶 為什麼這麼輕？硬體需求多低？

K3s 原本就是為資源有限、維運人力有限的場景設計。官方列出的適用情境包括 Edge、IoT、CI、開發環境、ARM 架構，以及無法投入大量 K8s 專業維運資源的情境。

🖥️ K3s Server 節點最低需求： 2 核心 CPU · 2 GB RAM
⚙️ K3s Agent 節點最低需求： 1 核心 CPU · 512 MB RAM
*註：以上為官方最低硬體需求，不包含工作負載本身（例如 Ollama 模型或 Open WebUI）。
🎁 開箱即用：單一執行檔內建完整電池

上游標準 Kubernetes 安裝完只是空骨架，需要自己挑選並安裝網路外掛 (CNI)、Ingress Controller、metrics-server 等。K3s 把常用的全部備好，這也是本週任務能在一臺 VM 上快速完成的原因！

containerd & runc Flannel (CNI) CoreDNS Traefik Ingress Klipper-lb (ServiceLB) Metrics Server Local-path-provisioner

📦 K3s 安裝完就已經附帶的 7 大內建元件（點擊列可凸顯重點）

內建元件 核心功能 與本週任務的關係（實戰必讀！）
containerd 與 runc 容器執行環境，K3s 不依賴 Docker 拉映像、跑 Pod。⚠️ 注意：K3s 的映像庫與 Docker 分開，本機 Docker 映像不會自動出現在 K3s！
Flannel Pod 之間的網路（CNI） 建立 Pod 虛擬網路，也是 Pod 連到主機 Ollama 的網路路徑基礎
CoreDNS 叢集內的名稱解析 (DNS) 讓叢集內的 Service 名稱能夠自動對應到 IP
Traefik Ingress Controller 對外 HTTP/HTTPS 入口，依網域規則讓流量導向 Open WebUI
Klipper-lb（ServiceLB） 讓 LoadBalancer 類型的 Service 在沒有雲端 Load Balancer 的環境也能運作 讓 Traefik 能對外接收流量，預設會綁定並使用主機的 80 / 443 埠
Metrics Server 提供 Pod 與節點的 CPU、記憶體即時用量 HPA 自動擴展的資料來源，執行 kubectl top 指令也靠它
Local-path-provisioner 用主機本機目錄提供 PersistentVolume 儲存 本週不使用（因為本課容器採無狀態 Stateless 設計）

*以上元件列表來自 K3s 官方 README，在進階應用中這些元件都可以透過啟動參數停用或替換（例如把 Traefik 換成 nginx Ingress）。

四、本課場景：前端交給 K3s，模型留在主機

為什麼不把 Ollama 模型也塞進 K3s 跟著一起複製 4 份？因為這個架構的核心哲學是：把「很重、不適合複製」的 LLM 模型留在主機，把「很輕、可以複製」的網頁前端（Open WebUI）交給 K3s 管理。

🗺️ 動態架構流程圖：使用者 ➔ Traefik ➔ Service ➔ Open WebUI Pods (1~4) ➔ 主機 Ollama
元件 放在哪裡 為什麼這樣設計？ 誰負責維持運作
Ollama 主機，由 systemd 管控 模型載入後占用大量記憶體：CPU 推論用系統記憶體，GPU 推論用 VRAM；Ollama 也自帶請求排隊機制（Ollama FAQ）。合理推論：多開一份只會多載入一份模型，把記憶體塞爆。 systemd
Open WebUI K3s 內的 Pod 合理推論：網頁前端本身運算量小，容易複製；各副本設定一致，就能互相替換分流。 Deployment 維持副本數，HPA 調整數量 (1~4)
Traefik K3s 內建的 Ingress Controller 對外只開 80 / 443 埠，依網域（如 qN.qqnice.org）導向 Open WebUI。 K3s
💡 為什麼這個場景選 K3s？
  • 一臺 VM 要同時跑 Ollama 與叢集，資源吃緊。K3s 官方最低需求是 Server 2 核心、2 GB RAM（不含工作負載），比自行組裝的完整 Kubernetes 輕量許多。
  • K3s 已內建 Traefik 與 Metrics Server，不必另外安裝就能直接做到 Ingress 與 HPA。
  • 單一節點就能完整體驗 Deployment、Service、Ingress、HPA 這組核心概念，之後換成多節點或雲端託管叢集（如 Azure AKS），觀念可以直接沿用！

五、這個架構的限制：誠實說明

本任務驗證的是 Kubernetes 的擴展與自癒機制，並不代表聊天服務的實際容量因此提高。有兩個關鍵限制一定要先說清楚：

⚠️ 限制一：增加 Open WebUI Pod，不會讓模型回答變快

Ollama 每個已載入的模型，預設一次只處理 1 個請求（OLLAMA_NUM_PARALLEL 預設為 1），其餘請求排隊；佇列預設上限為 512，超過就回傳 503 過載錯誤。調高並行數需要更多記憶體，所需 RAM 與 OLLAMA_NUM_PARALLEL × 上下文長度 (Context Length) 成正比（Ollama FAQ）。

🎯 核心觀念：瓶頸在模型推論端，不在網頁前端！
前端 Pod 再多，聊天請求還是要排隊等同一個 Ollama。真正要提高推論容量，需要在模型服務端擴充（例如更多 GPU 或主機，這不屬於本課範圍）。
👉 這也是任務書要求「壓測別打聊天 API」的原因：打聊天 API 會把壓力全卡在 Ollama 排隊，前端 CPU 根本不會升高，反而無法觸發 HPA！

⚠️ 限制二：Open WebUI 預設不支援直接多副本

Open WebUI 官方說明，標準映像檔是單一實例，內含嵌入式 SQLite、嵌入式 ChromaDB 與本機檔案儲存，這種設定不能直接多實例運行。水平擴展需要共享的持久化與協調服務（Scaling Open WebUI）。

🗄️ 互動實驗室 5：「本課教學簡化做法」vs「官方正式多副本架構」切換器
項目 🏢 官方多副本需求 (Production) 🎓 本課的簡化做法 (Lab) 若直接多開副本的後果與取捨
資料庫 外部共享 PostgreSQL（設定 DATABASE_URL） 每個 Pod 內建獨立 SQLite，不共享 各 Pod 資料彼此獨立，對話紀錄與帳號不會跨 Pod 保留（故本課採單一使用者模式）
即時協調 外部共享 Redis 不使用 缺乏跨實例即時狀態同步與 WebSocket 協調
WEBUI_SECRET_KEY 所有副本必須相同，否則發生登入循環與 401 錯誤 用 K8s Secret 注入，所有副本相同 這是本課唯一保持一致的憑證金鑰，避免 Session 驗證失敗
向量資料庫 (RAG) 必須使用外部向量資料庫 (如 PGVector, Qdrant, Milvus) 內建嵌入式 ChromaDB，不使用文件上傳與 RAG 嵌入式 ChromaDB 只允許單一程序寫入，多副本同時上傳文件可能導致程序崩潰！實作時請勿上傳文件。
檔案儲存 共享檔案系統 (NFS/ Ceph) 或物件儲存 (S3 / GCS) 不使用 上傳的檔案只會留在單一 Pod 內，換個 Pod 就讀不到

六、業界應用情境：K3s 適合用在哪裡？

K3s 適合資源有限、維運人力有限，卻仍想使用 Kubernetes 機制的場景。下表清楚標明哪些是官方列出的適用情境，哪些是根據課程脈絡的合理推論：

業界情境 為什麼適合 K3s？ 和本課架構的對應
🏭 邊緣與現場
（分店、工廠、IoT 閘道）		 官方適用情境 小型主機就能運行，現場沒有專職 IT 維運人員，靠 K8s 自癒機制自動維持服務不中斷。 合理推論：單節點 K3s 搭配本地 LLM 模型，提供工廠或分店現場使用的私有 AI 助理。
🔒 企業內部的私有 LLM 入口 合理推論 模型與對話都在自己的主機，不需把機密內容送到外部雲端服務，較容易配合內部資安與資料管理規定。 前端用 Open WebUI 多副本分流，模型留在主機。正式上線需要補齊第五節表格中的共享服務（PostgreSQL + Redis + 外部向量庫）。
🧪 開發與測試、CI 流水線 官方適用情境 一臺 VM 或筆電就能建出與正式環境相近的 K8s 叢集，快速建立、快速重置。 在把服務送上雲端託管 Kubernetes（如 AKS / GKE）之前，先在本地用 K3s 驗證 YAML 是否正確。
🎓 教學與實驗室、小型團隊自架 合理推論 一臺主機就能完整實作 Deployment、Service、Ingress、HPA 等物件，硬體門檻極低。 本週任務就是這個場景！
☁️ 和雲端託管 Kubernetes (AKS / EKS / GKE) 的關係

K3s 符合 Kubernetes 標準，所以你在這堂課學到的觀念可以直接移轉到雲端！
Open WebUI 官方的 Helm 部署文件說明，它可部署在任何 K8s 發行版上，包括 EKS、AKS、GKE、OpenShift、Rancher 與自架叢集。其中 AKS (Azure Kubernetes Service) 就是同學平常實作所在的雲端。

💡 差異主要在周邊元件：例如官方文件範例使用 nginx Ingress，而 K3s 內建的是 Traefik，設定與註解 (annotations) 寫法會不同；但 Deployment、Service、HPA 的概念完全相同。

🛑 什麼時候「不需要」K3s？

合理推論：如果是單一主機、單一服務、流量穩定、不需要自動擴展的情況（例如公司內部只有 20 人使用的簡單小工具），Docker Compose 已經非常足夠！

⚖️ 硬上容器編排反而會增加維運負擔。是否要用編排工具，要看的是實際需求，而不是工具本身是否流行。

七、本週任務與 Kubernetes 物件的對照（驗收與排錯指南）

三個驗收指標各自在驗證不同的機制。先知道「這一項在驗證什麼」，卡關時才知道從哪裡查！

驗收指標 背後驗證的 K8s 機制 ✅ 你應該看到的成功證據 🩺 失敗時先查哪裡？（排錯清單）
1. 對外服務正常 Ingress ➔ Service ➔ Pod 的路徑，以及 Pod ➔ 主機 Ollama 的連線 瀏覽器開得到網域（如 qN.qqnice.org），選取模型後送出對話有正常回覆 1. Traefik 是否拿得到主機 80/443 埠？
2. 主機 Ollama 監聽位址（OLLAMA_HOST）是否只綁了 127.0.0.1？
3. Open WebUI Pod 的 OLLAMA_BASE_URL 是否指對主機位址？
2. 動態擴展 HPA、Metrics Server、Pod 容器資源 requests 執行 kubectl get hpa -w 時 TARGETS 百分比上升，REPLICAS 從 1 增加到至少 3；停止壓測後縮回 1. TARGETS 顯示 <unknown>：檢查 Deployment 是否漏寫 resources.requests.cpu，以及 kubectl top pods 是否有數據。
2. 為什麼縮減很慢？縮減比擴展慢是正常的（預設 300 秒穩定視窗）！
3. 自動修復 Deployment 與 ReplicaSet 的控制迴圈，搭配 readinessProbe 手動刪除一個 Pod 後，新 Pod 自動出現並進入 Ready 狀態，且持續請求沒有整體中斷 1. 沒有設定 readinessProbe（新 Pod 還沒載入完就被塞流量導致報錯）。
2. 副本只有 1 個時刪掉那唯一 1 個，當然會造成短暫中斷。
💡 容易誤解的觀念 1：為什麼 HPA 顯示 <unknown>/50%？

HPA 的 CPU 使用率百分比是相對於 Pod 容器上所指定的資源基準量來計算的（HPA Walkthrough），實務上就是容器的 resources.requests.cpu。

公式：CPU 使用率 (%) = (Metrics Server 測得實際用量 ÷ Pod 設定的 requests.cpu) × 100%。
如果沒設定 requests，分母為無意義，K8s 算不出百分比，TARGETS 就會永遠顯示 <unknown>！

⏱️ 容易誤解的觀念 2：為什麼停止壓測後，Pod 很久都不縮回來？

縮減（Scale Down）比擴展（Scale Up）慢很多，是因為 Kubernetes HPA 縮減預設有 300 秒（5 分鐘）的穩定視窗（Stabilization Window）。

這是為了避免流量只是短暫呼吸波動，副本數就劇烈來回跳動（Thrashing / Flapping）（HPA API 參考）。這是刻意設計的保護機制，不是故障！

八、課堂討論題與名詞表

以下是課堂討論題，用來檢查自己是否真的理解（點擊題目可展開思考方向與參考解析）。驗收時的口頭問答另有題庫，不在此列。

Q1. 如果同時有 100 位同學對同一個 Ollama 送出聊天請求，增加 Open WebUI Pod 會改善什麼？不會改善什麼？ 點擊展開解析
✅ 會改善的部分：網頁前端靜態資源載入、介面回應、HTTP 連線處理能力（由 1~4 個 Open WebUI Pod 分擔前端流量）。
❌ 不會改善的部分：LLM 模型生成回答的速度與總推論吞吐量！因為後端只有同一個 Ollama 實例，且預設 OLLAMA_NUM_PARALLEL=1，100 個聊天請求依然要在 Ollama 佇列（上限 512）裡面排隊等模型一個一個算。
Q2. 你的公司只有一台主機、一個內部工具、使用者約 20 人。你會選 Docker Compose 還是 K3s？說明理由。 點擊展開解析
🎯 參考方向：選 Docker Compose。
單一主機、單一服務、20 人流量非常穩定且不需要動態水平擴展（HPA）。使用 Docker Compose 設定簡單、起步與維運成本最低；若硬上 K3s 反而要多維護 Deployment/Service/Ingress 等 YAML 與叢集元件，增加不必要的複雜度。工具選擇應看實際需求而非流行度。
Q3. 畫出一個請求從瀏覽器到 Ollama 回覆的完整路徑，標出每一個經過的元件。 點擊展開解析
🗺️ 完整請求路徑：
1. 使用者瀏覽器輸入網址（如 https://qN.qqnice.org）
2. 進入主機的 80/443 埠，由 Klipper-lb (ServiceLB) 轉交給 K3s 內建的 Traefik (Ingress Controller)
3. Traefik 根據 Ingress 規則比對網域與路徑，轉發給對應的 Open WebUI Service
4. Service 透過負載均衡，將請求分發給其中一個狀態為 Ready 的 Open WebUI Pod
5. Open WebUI Pod 根據 OLLAMA_BASE_URL，跨出 Pod 網路空間（經由 Flannel CNI 與主機內網介面）連線至主機由 systemd 管理的 Ollama (Port 11434)
6. Ollama 排隊推論完成後，將 Token 串流沿原路回傳給使用者瀏覽器。
Q4. 把 Open WebUI 的資料改放 PostgreSQL 與 Redis 之後，哪些問題會消失？哪些新元件要自己維運？ 點擊展開解析
✨ 會消失的問題：
1. 不同 Pod 之間對話紀錄與使用者帳號不一致的問題會消失（所有 Pod 讀寫同一個 PostgreSQL）。
2. 可以開啟多使用者登入，且透過 Redis 完成跨副本的即時協調與狀態同步。
🛠️ 新增需要自己維運的元件：
除了 PostgreSQL（資料庫備份、高可用）與 Redis 之外，若要使用知識庫上傳文件與 RAG 功能，還必須額外維運外部共享向量資料庫（取代嵌入式 ChromaDB）以及共享檔案儲存 / 物件儲存 (如 S3/NFS)。
Q5. K3s 預設內建 Traefik。如果公司已經標準化使用 nginx Ingress，你會怎麼處理？ 點擊展開解析
🔧 處理方式：
K3s 的所有內建元件都是可以停用或替換的！可以在安裝或啟動 K3s Server 時加上參數 --disable=traefik 停用內建的 Traefik，接著再用 Helm 或 YAML 安裝公司標準的 nginx Ingress Controller。這正是 K3s 符合標準 Kubernetes 的好處：Deployment、Service、HPA 完全不用改，只需調整 Ingress 的 Controller 與對應 annotations。
