使用無 Agent 輕量級機制，直接調用系統底層 Rsyslog 套件，透過 UDP 無交握高效協議轉發全部日誌。

為什麼選擇本機 Rsyslog 轉發？

  • 極低資源消耗：免安裝額外的 Agent（如 Filebeat），原生自帶極輕量。
  • 完美相容性：Ubuntu 24.04 出廠預設整合，與系統開機腳本同步啟動。
  • 配置維護省心：僅需一行設定即可運作，格式穩定可靠。

部署前哨提醒 (Pre-flight Check)

  • 確保 Ubuntu 機器可以 Ping 通 Graylog 伺服器：ping 10.24.1.1
  • Graylog 的 Syslog UDP Input **必須設定在 1024 以上的連接埠**，因為系統不允許非 root 身分程序占用核心特權 Port（如 514）。

Graylog Server 本地防火牆限制

安全性核心

若有啟用系統防火牆 (UFW)，請開啟指定的 UDP 規則。強烈建議**僅放行特定的 Linux 來源端 IP**：

首選建議
【限制特定來源】僅允許指定 Ubuntu Client 連線：
sudo ufw allow from 10.24.1.100 to any port 30514 proto udp
【全面開放】快速測試（任何 IP 均可發送）：
sudo ufw allow 30514/udp

Graylog Server 狀況排查診斷手冊 (Troubleshooting)

運維核心

新痛點：Graylog Server 9000 Port 怎麼樣都連不上、網頁打不開？

Graylog 的底層架構強烈依賴 **MongoDB** (儲存設定、Dashboard、Metadata) 與 **OpenSearch / Elasticsearch** (儲存龐大的日誌數據)。 若這兩大資料庫服務其中一個掛掉、或 Graylog 連不上它們，Graylog Server 就會卡在初始化階段並陷入不斷重啟，此時 **9000 port 當然就不會開啟**。

步驟 1：診斷 MongoDB 運作狀態

MongoDB 必須優先成功啟動，Graylog 才能讀取它的開機 Metadata。請檢查其系統服務：

sudo systemctl status mongod

*(備註：部分舊版系統服務名稱可能為 mongodb)*

步驟 2：排查 OpenSearch / Elasticsearch 與 Port 9000 狀況

確認 Graylog 的監聽埠狀態，並嘗試重啟日誌儲存引擎：

A. 先檢視目前系統開放的所有 Port 狀態：
sudo netstat -tnpl
B. 重啟 OpenSearch / Elasticsearch 服務 (排查其假死)：
sudo systemctl restart opensearch

*(若您使用的是 Elasticsearch，請重啟 elasticsearch)*

C. 再次驗證 9000 Port 是否被成功拉起：
sudo netstat -tnpl

狀況 2：Graylog Input 呈現 RUNNING，但搜尋頁完全沒有任何日誌

這通常是**網路連通性**或**防火牆攔截**所致。UDP 是無連接協議，即使目的地防火牆阻擋，發送端 Rsyslog 也不會報錯。請直接在 Graylog Server 執行抓包確認：

sudo tcpdump -i any udp port 30514 -nn -vv -X
  • 有抓到封包：代表封包已抵達，問題出在 Graylog 內部的 Index 寫入或 Stream 過濾器。
  • 完全無封包：請檢查 Ubuntu Client 是否能路由到 Graylog，或中間是否有雲端安全性群組 (Security Group) 阻擋該 UDP Port。

狀況 3：新建 Input 狀態呈紅色的 FAILED 且無法啟動

此狀況高機率為**Port 被佔用**或**權限不足**：

  • 檢測 Port 是否已被其他程序佔用：在 Graylog 主機執行以下命令：
    sudo ss -tulnp | grep 30514
  • 核心權限問題：若您將 Port 設為標準 Syslog Port 514，非 root 權限執行的 Graylog 將會啟動失敗。**強烈建議使用 1024 以上的 Port (如 30514)**。

狀況 4：出現 Cluster Blocked / Index Read-Only 鎖定錯誤

這是最經典的 Graylog 停止接收狀況。當後端的 Elasticsearch/OpenSearch 所在磁碟空間**超過 95% (Watermark Floodstage)**，系統會自動將所有 Index 鎖定為**唯讀 (Read-only)**，導致 Graylog 完全無法寫入新日誌。

錯誤特徵 (出現在 Graylog Server Log 中)：

"flood stage disk watermark [95%] exceeded on ... all indices on this node will be marked read-only"

💡 排除步驟：

  1. 清理 Graylog 主機磁碟空間，釋放至 90% 以下。
  2. 執行以下 API 指令向 Elasticsearch 發送請求，解鎖唯讀限制：
    curl -X PUT "http://localhost:9200/_settings" -H 'Content-Type: application/json' -d '{"index.blocks.read_only_allow_delete": null}'
// 即時監看 Graylog 系統運作狀況與詳細 Exception 拋出：
sudo tail -f /var/log/graylog-server/server.log -n 100

Ubuntu Client 端 Rsyslog 配置

進入目標 Ubuntu 伺服器，寫入獨立轉發設定檔並重啟服務機制。

1

檢查並啟動 Rsyslog 套件

多數 Ubuntu 環境均已預裝，但仍建議做一次狀態檢驗與更新：

sudo apt update && sudo apt install rsyslog -y && sudo systemctl enable --now rsyslog
2

建立並寫入專用子配置檔案

請於 /etc/rsyslog.d/ 目錄建立新檔案。不要去修改原本主設定檔，避免未來作業系統更新衝突：

sudo nano /etc/rsyslog.d/99-graylog.conf
寫入內容 (貼入 nano 編輯器中)： 
*.* @10.24.1.1:30514
註: *.* 表示發送所有日誌。@ 代表 UDP，若要切換 TCP 請改為 @@。
3

重載 Rsyslog 引擎

儲存檔案並離開後，請重新啟動 Rsyslog 以讀取新規則：

sudo systemctl restart rsyslog
